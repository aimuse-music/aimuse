2. 既存データを壊さずに適用できるか

  • データ：会員・曲・お気に入り・フォロー・レビュー・通報・再生記録・ファイル・削除記録の全行を、適用前後で比べて変化なし 確認済み
  • やり直し：同じSQLを2回実行しても壊れない／前提の版が無ければ何も変更せずに中止 確認済み
  • 途中で失敗した場合：各SQLは1回の実行が1つのまとまり（途中で失敗すると全体が取り消される）になるよう書いています。SQL Editor が1回の実行をまとめて扱うことは PostgreSQL の仕様に基づく判断で、本番の画面では 未確認
  • 止まる時間：列の追加は既定値なし・チェックは空の列だけなので一瞬です。follows の索引作成の間だけ、フォローの登録が数秒待たされる可能性があります（今の件数なら1秒未満の見込み）
  • 本番特有の違い：保存場所 avatars がすでにある場合や、同じ名前の関数が既にある場合に備え、読み取り専用の事前確認SQL（release_preflight.sql）で先に確かめます

3. GitHub の Revert だけでは戻せないもの

詳しい手順は下の「復旧方法」にまとめました。要点は次のとおりです。

  • データベース：版ごとの「元に戻す用SQL」を新しい順に実行します（ローカルで適用前と完全に同じに戻ることを確認済み）。追加した列・表・データは消さずに残します
  • Service Worker（PWA）：Revert するだけでは、利用者の端末に入った Service Worker は残ります。緊急停止用の sw.js に差し替えて公開します（動作確認済み）
  • Edge Functions・Cron：GitHub とは別に Supabase 側で止めます（関数の削除・合言葉の削除・Cron の停止）
  • 完了した完全削除：元に戻せません。そのため、実環境の検証はテスト用アカウントだけで行います

select status, requested_at, purge_after, attempts, last_error,
       files_done_at, db_done_at, finished_at
from aimuse_private.account_deletions order by requested_at desc limit 20;

-- テスト用アカウントだけ申請できるようにする（承認後のみ）
insert into aimuse_private.deletion_testers (user_id, note)
select id, 'テスト用' from auth.users where email = 'テスト用のメールアドレス';
update aimuse_private.settings set value = 'testers' where key = 'account_deletion_mode';

-- すぐに止める（受付・完全削除とも）
update aimuse_private.settings set value = 'off'
where key in ('account_deletion_mode', 'account_purge_enabled');

-- テスト用アカウントだけ、削除の開始を今にする（承認後のみ）
update aimuse_private.account_deletions set purge_after = now()
where status = 'pending'
  and user_id = (select id from auth.users where email = 'テスト用のメールアドレス');
